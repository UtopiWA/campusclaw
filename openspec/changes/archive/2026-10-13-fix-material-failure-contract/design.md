# Design

## Context

参见 [proposal.md](proposal.md)。当前后端已按异步契约返回 `processingStage`、`failureCode` 和 `retryable`，但主 `auth-upload` 的在线查看/下载要求混入两个旧上传场景，材料页也只消费失败代码而未展示失败阶段。上传弹窗中的请求失败目前写入页面级错误区，该区域位于模态遮罩之后，导致用户在弹窗保持打开时看不到错误。本次不改变已经稳定运行的后端状态机。

## Goals / Non-Goals

**Goals:**

- 让主规格对请求内校验、主事务失败和后台解析失败只有一套无冲突语义。
- 使用面向用户且脱敏的中文标签展示失败阶段，与失败原因分开表达。
- 让上传请求错误在当前操作上下文中立即可见，并允许用户直接更换文件重试。
- 用组件测试锁定失败阶段与失败代码同时可见的行为。

**Non-Goals:**

- 不修改 API、数据库字段、枚举、异步执行器、恢复调度或权限判断。
- 不展示 `indexError`、堆栈、供应商响应、内部地址或存储路径。
- 不重新设计材料列表或增加新的失败操作。

## Decisions

### Decision 1: 显式移除旧 Requirement，并新增职责单一的文件访问 Requirement

OpenSpec 不允许 `MODIFIED Requirement` 静默删除已有 Scenario，因此 delta 明确移除混合了文件访问和旧上传语义的“教学材料在线查看与下载”，并新增“教学材料文件访问”承接五个有效场景。异步上传、后台失败和主事务补偿继续由“教学材料上传与知识库入库”Requirement 统一规定。

选择理由：归档历史必须保持不可变；显式 `REMOVED` 与 `ADDED` 能留下删除原因和迁移关系，并通过 OpenSpec 的防误删校验。备选直接编辑主规格虽然更快，但无法留下可审核的纠正过程；保留旧 Scenario 名称再改写内容仍会误导读者。

### Decision 2: 失败阶段使用固定中文映射，不直接显示内部枚举

材料页增加阶段格式化函数，在 `FAILED` 行中明确显示例如“失败阶段：正文解析”“失败阶段：索引构建”或“失败阶段：任务调度”。未知或缺失值使用“后台处理”兜底；失败原因继续由既有稳定 `failureCode` 映射生成。

选择理由：阶段枚举是稳定的 API 信息，但直接显示 `PARSING/INDEXING` 不符合现有中文界面；阶段和原因分开展示可以区分“在哪里失败”和“为什么失败”。备选仅根据 failure code 推断阶段并不可靠，例如 `PROCESSING_ERROR` 可发生在多个阶段。

### Decision 3: 前端测试断言可观察文案

扩展失败材料组件测试，同时断言阶段文案、失败原因和教师重新处理操作；至少覆盖 `INDEXING`，并用参数化或独立用例覆盖 `PARSING` 与兜底行为。

选择理由：后端 DTO 测试只能证明字段存在，不能证明页面实际消费字段。测试继续使用纯文本断言，不依赖 CSS 或内部函数实现。

### Decision 4: 上传请求错误留在弹窗内处理

材料页为上传操作维护独立的 `uploadError`。上传开始或用户选择新文件时清空旧错误；请求失败时保持弹窗和已选文件，并在文件选择区附近以 `role="alert"` 展示错误；成功或关闭弹窗时清理该状态。页面级 `error` 继续负责查看、下载、重命名、删除等弹窗外操作。

选择理由：失败后自动关闭弹窗会中断当前操作并迫使用户重新选择文件；把错误留在弹窗内既能保证可见性，也能保留修正上下文。错误仍使用 API 的脱敏消息，不新增后端错误结构。

## Risks / Trade-offs

- [失败信息增加后材料行可能变高] → 使用现有失败文案区域和紧凑分隔，不增加新卡片或弹窗。
- [历史数据可能出现 `QUEUED` 或缺失阶段] → 提供任务调度和通用兜底文案，不把未知值暴露给用户。
- [上传错误使弹窗内容变高] → 复用紧凑的反馈样式，模态框继续使用既有最大高度和滚动行为。
- [只清理一个 Requirement 可能遗漏其他矛盾] → 实现前后分别搜索非法 UTF-8、回滚和后台解析表述，并执行全量 OpenSpec 严格校验。

## Migration Plan

1. 先合并并校验主规格纠正 delta。
2. 发布材料页阶段文案和组件测试；后端与数据库无需迁移。
3. 人工检查解析失败与索引失败材料在桌面和窄屏下均能看见阶段、原因和允许操作。
4. 若前端需要回滚，可回退展示改动；主规格的冲突清理不应回滚。
